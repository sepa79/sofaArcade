# War for Crown C64 Map Generation Analysis

## Goal

The map generator target is:

- preserve the C64 province-growth logic,
- use a modern deterministic RNG with the same requested ranges,
- keep map-preview controls outside the rules screen,
- produce water-heavy continents with bays, holes, and irregular province shapes.

Exact C64 byte-for-byte map reproduction is not a practical seed-based goal
because the original random routine reads `$D012` raster timing. The practical
acceptance target is identical growth logic with deterministic modern RNG. If
the growth logic is actually identical and each random choice uses the same
range at the same decision point, the generated maps should have the same
visual character as C64 maps even when exact seed-to-seed reproduction is not
possible.

## Known C64 Layout

Owner reverse-engineering notes and C64 code inspection point to:

- flat tile buffer base: `$C400`,
- tile count: `$F0` = 240 cells,
- C64 map dimensions: 20 by 12,
- neighbour direction offsets:
  - right: `+1`,
  - left: `-1` / `$FF`,
  - down: `+20` / `$14`,
  - up: `-20` / `$EC`.

The high bit `$80` is used as a transient "in progress/frontier" marker during
province growth.

## Random Routine

The shared routine at `$218B` does not use SID noise in the inspected ASS/GDG
modules. It reads raster line timing:

```asm
$218B  LDA $D012
$218E  ADC $E000
$2191  ADC $219B
$2194  STA $219B
$2197  INC $218F
$219A  RTS
$219B  .byte $00
```

For the TypeScript generator, use the existing deterministic `Rng` interface.
Calls that used `JSR $218B` followed by `AND #$03` become
`rng.nextIntInclusive(0, 3)`.

## Exact Setup And Growth Kernel

Evidence: `menue:L5101..L520F`.

The C64 map generator in the inspected `ERBENT1A` module is fully visible in
`menue`, not only in the later growth kernel.

### Initial Water And Empty Land Setup

`menue:L5101` creates a byte buffer at `$C400`:

1. writes `$FF` from `$C414` through `$C4FF`;
2. writes water `$00` to the top row `$C400..$C413`;
3. writes water `$00` to the sentinel/bottom band `$C4F0..$C503`;
4. for each top-row column, with 50% chance writes water to `$C414 + column`;
5. for each bottom visible column, with 50% chance writes water to
   `$C4DC + column`;
6. for twelve row starts from `$C414` to `$C4F0`, writes water to the left and
   right borders;
7. for those same rows, with independent 50% chances writes water to the inner
   left and inner right border-neighbour cells;
8. places nine additional random water cells by repeatedly calling RNG until it
   lands on a `$FF` byte, then writing `$00`;
9. scans tiles `$15..$EF` and calls `kernal:L216B`; when the helper returns
   zero, the tile is forced to water. This removes land candidates with no
   orthogonal non-water neighbours according to the C64 neighbour test.

The visible map is still 20 by 12 (`$F0` bytes). The setup also writes a
sentinel band past the visible 240 bytes so neighbour reads at the lower edge do
not need defensive bounds checks.

### Cleanup Predicate

Evidence: `kernal:L216B`, fixture
`fixtures/kernal-l216b-map-cleanup-neighbors.json`.

The helper receives the current flat tile index in `Y` and inspects four
orthogonal neighbours in this order:

1. left: `Y - 1`;
2. right: `Y + 1`;
3. down: `Y + 20`;
4. up: `Y - 20`.

It returns immediately with the first nonzero neighbour value in `A`. If all
four neighbours are zero, it returns `A = 0`. The setup pass keeps a land
candidate when this helper returns nonzero and turns it into water when it
returns zero.

Important port detail: the helper treats any nonzero byte as land/connectivity,
including `$FF` empty land, committed province ids, and `$80` high-bit pending
values. During the initial setup cleanup the relevant normal case is `$FF`
empty land versus `$00` water.

### Province Seeds And Terrain

After water setup:

1. for each province id from `$C8A1` down to `1`, RNG chooses a starting byte;
2. the code increments `Y` until it finds a `$FF` empty land tile;
3. that tile receives the province id;
4. the seed tile is stored in `$C512 + province`;
5. terrain is generated by `rngByte & 7`, retrying while the result is `0`;
6. terrain id `1..7` is stored in `$C576 + province`.

So the original has exactly seven non-water terrain ids. Water is `$00` in the
tile buffer and terrain ids are attached per province, not per tile.

Terrain retry evidence: `fixtures/menue-terrain-assignment-range-retry.json`.
The fixture enters `menue:L5197` directly and proves that byte values producing
`1..7` after `AND #$07` are stored as terrain ids, while a zero result branches
back and consumes another RNG byte.

### Province Growth

The recovered kernel behaves like a compact multi-source frontier growth pass:

1. Iterate through the flat map buffer using `Y` as the current tile index.
2. Ignore water and unused tiles.
3. For each active/frontier province tile, try up to four random directions.
4. A target tile is usable only when it is still marked as empty.
5. On success, write the current province value OR `$80` to the target tile.
6. Continue scanning until the map end is reached.
7. Clear `$80` markers after the pass.
8. Restart generation when the pass cannot grow enough tiles.

The direction retry loop uses a mutable counter at `menue:L520B`, with the
direction table at `menue:L520C`:

| Index | Byte | Meaning |
| --- | ---: | --- |
| `0` | `$01` | right |
| `1` | `$FF` | left |
| `2` | `$14` | down |
| `3` | `$EC` | up |

## Golden Fixture

Fixture: `fixtures/menue-map-generation-sequential-rng.json`.

The fixture loads `kernal` at `$0800` and `menue` at `$3000`, replaces
`kernal:L218B` with a deterministic byte stream `1, 2, 3, ...`, then executes
the real `menue:L5101` generator with `$C8A1 = 30`.

Confirmed output:

- RNG counter `$02FB` ends at `$DD`;
- visible map buffer is exactly `$C400..$C4EF`, 20 by 12 bytes;
- visible map contains 79 water tiles and 161 land tiles;
- province ids `1..30` are committed and no `$80` pending markers remain;
- province seed tiles are written at `$C512 + province`;
- terrain ids are written at `$C576 + province`.

This is the byte-level acceptance fixture for the C64 scanline generator under a
known RNG stream. It proves the full call order and ranges for the executed
path, including setup, seed placement, terrain assignment, and growth. It does
not claim raster-RNG seed equivalence, because the original random routine reads
timing from `$D012`.

## Self-Modifying Details

The generator uses C64-style mutable code/data. Known patterns:

- `DEC` and `INC` opcodes differ by bit `$20`.
- `EOR #$20` can flip such an opcode in place.
- The direction table and retry counter live inline near the growth routine.
- The earlier visible screenshot was missing enough surrounding code to prove
  the claim write. The full listing resolves it: `menue:L51D6` executes
  `lda $C400,y; ora #$80; sta $C400,x`.

Do not port the self-modifying structure literally. Port its state transitions
explicitly in pure TypeScript.

It also adds practical map validation:

These are good preview-layer behaviours, but they are not automatically the
C64 kernel. Keep them as explicit modern options around the base generator.

## Current Implementation Slice

The TypeScript generator should use a C64 scanline growth model, not the older
temporary "water mask first, then modern frontier queue" placeholder.

Current implementation target:

1. Keep the default preview-style map at 20 by 12 and 16 provinces.
2. Use a byte-array model matching the C64 buffer semantics:
   - `$FF` = empty land candidate,
   - `$00` = water/unusable,
   - `$01..$7F` = committed province owner,
   - owner OR `$80` = pending owner written during the current pass.
3. Port the recovered `menue:L51A6..L5207` growth loop directly:
   - `X = 0`, store previous empty count,
   - `Y = $15`,
   - scan until `Y == $F0`,
   - skip water/empty/pending values,
   - for committed province tiles, draw one random direction `0..3`,
   - retry by decrementing that direction modulo 4,
   - claim only targets whose value is exactly `$FF`,
   - write `currentOwner | $80`,
   - after the scan, clear pending high bits and count remaining `$FF` tiles,
   - restart generation if the remaining empty count did not decrease,
   - finish when the remaining empty count is zero.
4. Keep modern seeded RNG only as the replacement for `JSR $218B`.
5. Port the recovered `menue:L5101..L519F` setup pass as the `c64-original`
   generator baseline.

This is now a direct port target for the inspected `ERBENT1A` map generator,
with one deliberate difference: the RNG source is injectable and deterministic
instead of C64 raster timing.
